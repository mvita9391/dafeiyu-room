# 初始世界、存档与家具资源

## 不是两个数据库

项目有一份随代码发布的初始配置，以及每次安装自己的运行数据库。

| 内容 | 位置 | 谁会修改 |
| --- | --- | --- |
| 卧室、客厅、院子、便利店的发布默认布局 | `shared/world/starter-world.json` | 开发者显式发布 |
| 家具种类、占地、交互与可放置规则 | `shared/layout.js`、`shared/world/catalog.js` | 更新代码 |
| 家具造型与固定景物 | `src/world/` | 更新代码 |
| 公开角色运行模型及清单 | `resources/character/` | 更新资源并核对清单 |
| 实际场景、通道、家具摆放、角色需求、动作记录、授权、事件 | `data/game.sqlite` | 玩家、智能体和服务运行时 |

新安装先从初始配置创建世界，以后使用自己的数据库。已有旧版家具布局会按迁移规则保留。已存在的世界不会因为重启、更新代码或修改默认配置而重新初始化。角色实时坐标保存在内存，重启服务后角色从默认出生点进入。

在卧室、客厅、院子或街角便利店打开「设置 → 恢复默认」，确认后会用当前游戏版本随附的默认布局替换当前场景的家具摆放。旧存档也可以用这个操作换上新版布局。

## AI 修改会保存吗

通过 MCP `build_apply` 成功应用的场景、通道和家具变化会入库，刷新网页后仍然存在。`build_preview` 只签发预览方案，尚未改变世界。

运行数据库不提交到 Git。AI 的日常世界工具不会写入初始配置、生成 Git 提交或推送仓库。

当前 MCP 从批准的家具与模板目录选择物件，不能通过描述直接生成新 GLB，也不能任意上传并执行模型文件。游戏代码增加新家具后，所有用户更新代码即可在目录中选用；实际摆放后才在数据库中新增实例。

## 更新发布默认布局

在项目目录主动运行：

```bash
npm run world:publish-default
git diff -- shared/world/starter-world.json
```

检查差异后，再提交代码并按自己的发布流程推送仓库。这个命令本身不提交、不推送，也不修改运行存档。

导出范围仅为当前的 `bedroom`、`living`、`yard`、`convenience-store` 四个场景及它们之间的通道。其他运行场景会提示未发布，不会自动加入初始世界。只导出布局白名单字段，不导出人物位置、需求数值、会话、授权、控制租约或事件。

目前初始布局导出不支持家具承托关系；遇到这类实例会报 `STARTER_SUPPORT_UNSUPPORTED`，不会悄悄丢失关系。需要扩展发布格式后再发布这类布局。

新旧存档都可从快速传送选择「森林 → 入口」或「森林 → 湖泊」。首次传送会按内置模板创建森林并保存到当前存档，已有森林会直接复用。通过快速传送创建的森林可以用同一菜单返回院子，院子的门和布局维持原样。

高级用法可指定来源数据库与输出 JSON：

```bash
node scripts/publish-starter-world.mjs --database /secure/save.sqlite --output /secure/starter-preview.json
```

发布命令不是常规保存按钮。平时摆家具后等待页面显示保存成功即可。

## 备份与恢复

1. 停止游戏服务。
2. 备份整个 `data/` 目录，包括同目录下的 `game.sqlite.mcp-json.key`（如果存在）。桌面版使用独立存档时，备份它实际使用的数据目录。
3. 恢复时保持服务停止，将备份目录放回原位置后再启动。

SQLite 使用 WAL；服务运行时只复制一个 `.sqlite` 文件，可能遗漏尚在日志中的数据。停止服务后备份整个目录最直接。

数据库也包含授权和主人会话。备份应放在受保护的位置，不要提交仓库或公开下载。需要完整恢复游戏时，还要保留相匹配的项目代码与模型资源；单独的数据库不包含 GLB 模型。

不要为了刷新初始布局直接删除数据库：这会同时丢失个人世界、授权和事件。修改发布默认配置不会主动重置自己的存档。

便利店首次接入：服务启动时通过一次性功能升级新增店外场景，将客厅原来的院子门改接便利店并添加返回入口。已有家具与农田不重置；升级标记写入运行存档，后续重启不会再次覆盖玩家或智能体的修改。
