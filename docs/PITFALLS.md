# 踩坑日记

整理日期：2026-11-04。记录已经遇到的问题、代码层面的原因和当前处理方式；不把实验结果写成通用保证。

## 1. 模型好看，不等于适合直接绑定动作

**现象**：图生 3D 的角色静止时可爱，走动时手、裙子和头发被拉扯，局部还存在粘连。

**原因**：细节丰富的表面不代表有适合变形的拓扑、独立部件和正确蒙皮。Q 版比例又与通用人体骨架有较大差异。提高面数不能直接修好权重。

**处理**：保留原始模型和 Blender 源文件，使用经过骨骼及权重适配的活泼版作为默认角色。头发、尾巴和手部动作分别处理。程序动作仍是原型方案，局部穿插需要继续打磨。

**经验**：检查模型时同时看静态外观、关节变形、部件是否可分离、材质贴图和目标动作。不要只比较正面截图。

## 2. 后端权威移动直接驱动画面，WASD 出现延迟和顿挫

**现象**：接入持久世界后，人物走走停停；增加插值后画面顺了一些，按键却明显延迟。

**原因**：把玩家每帧移动改成短距离网络命令，画面等待后端位置；旧动作又被反复取消重建。路径节点损失步长、直线路径被网格折线带偏，也会造成不匀速。统一加插值缓冲进一步增加了玩家操作延迟。

**处理**：玩家使用本地逐帧预测；前后端共用输入积分和碰撞检查。服务端按序确认输入，客户端重放未确认部分。玩家操作绕过网络插值缓冲，智能体的服务端动作仍使用插值展示。移速恢复为 2.82 米/秒。

**经验**：服务器保存真实状态，不代表画面必须等待每次网络确认。要分别验证持续移动、转向、松键、旧确认、碰撞和过门。

## 3. 状态在后端变了，人物仍然只会站着

**现象**：吃饭没有动画，睡觉站在床上，坐椅子高度不对。

**原因**：后端 `eating`、`sleeping`、`seated` 没有完整映射到人物展示；吃饭被当成待机，睡觉使用了不匹配的状态。渲染又覆盖了骨骼已经计算出的座面高度。

**处理**：增加统一的状态展示适配，吃饭显示白饭碗和手臂动作，睡觉沿床方向躺下，坐姿按髋部与座面高度对齐；离开动作时恢复相应姿势。

**经验**：后端状态测试通过，不能证明前端动画正确。需要检查实际模型画面和动作结束后的恢复。

## 4. 移除快捷按钮时，把家具交互入口也漏掉了

**现象**：底部“坐下、游泳、滑梯”按钮移除后，椅子没有可用入口；电脑前椅子的接近点还会被桌子挡住。

**处理**：点击家具时回溯到准确的家具实体，再提交交互。默认接近点不可达时尝试侧面路线。只处理最近家具，避免点击桌子却穿透选中后面的椅子。

**经验**：快捷按钮和世界物件交互是两条入口。物件的坐标、缩放、朝向与碰撞范围都要参与交互点计算。

## 5. 坐了两秒就“掉下来”

**原因**：原先坐下是两秒的有限动作，完成时统一回到地面。动画已经正确，生命周期仍然错误。

**处理**：坐下动作可以返回 `completed`，同时将持续坐姿保存到角色的休息状态。计时结束、控制租约到期和重启不会自动把人物放回地面；移动或新动作会安全起身。座椅被移动或移除时会退出旧坐姿。

**经验**：动作完成和姿势保持应分开。否则智能体要么一直等待，要么人物刚坐稳就站起来。

## 6. 世界名猜错，被误认为授权丢失

**现象**：智能体猜测 `main`、`home` 等世界名，收到 `UNAUTHORIZED`，不断尝试重新授权。

**原因**：原先把世界授权范围不匹配与凭证失效合并报错，工具说明也没有强调可省略参数。

**处理**：首次调用 `world_enter {}`。填错世界名返回 `WORLD_SELECTION_INVALID`，给出当前凭证已授权的世界与重试方法；不会探测或列出未授权世界。失效、过期或撤销的凭证继续在连接层返回 401。HTTP 和 stdio 都提供初始化说明。

**经验**：认证成功、世界选择、操作权限应分别解释。不能靠每个宿主自己补一段提示词来避免同样的问题。

## 7. “亲密”栏显示的其实是精力

**原因**：旧 UI 的亲密字段被临时用于展示后端精力，标签没有同步修改。

**处理**：精力使用独立字段，左下角明确标为“精力”，显示一位小数。心情对应 `happiness`，饱食对应 `100 - hunger`，精力对应 `energy`。

**经验**：数值定义和界面名称必须一致。精力为 0 当前不会禁止移动、减速或导致死亡；吃饭降低饥饿，睡觉恢复精力，不要让智能体自行想象不存在的限制。

## 8. 默认世界与个人存档容易混淆

**现象**：本地摆好的卧室和院子，与新用户首次下载看到的布局不完全一致。

**处理**：将选定的三个场景固化到 `shared/world/starter-world.json`。首次启动用它初始化数据库；已有世界不会被默认配置覆盖。AI 改造只写个人数据库。只有显式运行 `npm run world:publish-default` 才更新发布布局。

**经验**：不要把个人 SQLite 提交到仓库，也不要每次启动都把默认配置覆盖到存档。家具目录随代码更新，摆放实例才入库。

## 9. 智能体汇报后总是停止，不一定是游戏故障

**观察**：外部宿主的一轮记录中，智能体汇报后仍查询过动作状态，随后主动释放控制、等待消息并设置潜水。回合正常完成，没有用尽操作额度。

**排查发现**：静态预设允许继续探索，但动态回复检查仍引导等待和收尾；短期聊天回合没有独立的持续世界活动状态。语音发送耗时也可能消耗控制租约。

**结论**：游戏能继续执行已经接受的动作，不能代替宿主决定模型何时再次运行。把“100 个动作上限”调大，不会自动产生探索目标。

**宿主侧建议，尚不是游戏内置功能**：将世界活动与 QQ 聊天回合分开保存；汇报后可跨回合恢复进度，用户叫停或预算到期时停止。普通聊天继续保持安静策略。具体要求见[提示词文档](MCP-PROMPTS.md)。

## 10. 缺少通用资源读取工具，不代表没有地图

普通 MCP 工具已经提供替代入口：`world_observe` 查地图和物件，`catalog_list` 查家具与模板，`world_get_events` 查事件。宿主应先开放这些已有工具，而不是让智能体盲走或编造观察结果。

## 11. 家具只有外观目录，还不足以供 AI 摆放

新增秋千等家具时，需要同时接入模型工厂、编辑器分类、类型白名单、MCP 参数校验、占地范围、交互点与保存恢复。秋千还有摆动座面的视觉偏移，人物要跟着座面移动。

**经验**：展示模型做出来后，还要验证可摆放、可保存、可通过 MCP 建造。新物件加入目录不代表自动摆进初始场景，也不能侵占保护农田。

## 查问题时的顺序

1. 从实际调用、返回值和事件时间线确认发生了什么。
2. 区分游戏、网页、智能体和宿主各自的职责。
3. 用隔离数据库复现，避免测试污染个人存档。
4. 同时验证状态与画面，不把“接口成功”当成“体验正确”。
5. 日志只保留排查所需字段，不把真实凭证、会话令牌或个人聊天放进公开仓库。
